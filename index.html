CLI vs MCP：Agent 工具调用架构的深度辨析与选型指南

发表于 2026-09-07 分类于 Agent

引言：一场正在发生的架构之争

2025 年以来，AI Agent 领域爆发了一场关于工具调用架构的激烈争论。一方认为 MCP（Model Context Protocol）作为 Anthropic 提出的开放标准，将成为 Agent 连接外部工具的事实标准；另一方则提出”CLI 会取代 MCP”的判断，认为命令行工具配合 Skill 文档的模式在 context 经济性、可组合性和模型亲和性上具有本质优势。

这场争论并非单纯的技术偏好之争，它触及了 AI Agent 架构的核心问题：**大语言模型应该以何种方式与外部世界交互？**是通过标准化的结构化协议，还是通过灵活的文本命令？这个问题的答案将直接影响未来 Agent 平台的生态格局、开发者的接入成本，以及最终用户的体验。

本文以美团开放平台的真实 Skill 实践为切入点，完整拆解两种架构的交互流程，从七个维度进行系统对比，并结合第一性原理和历史类比，给出深度的选型决策框架。

**核心论点预告**：CLI 与 MCP 不是取代关系，而是分层关系。CLI 正在抢走"交互层"的主战场，而 MCP 在"连接层"的标准化与安全边界短期内不可替代。最终的收敛形态是"Skill 交互层 + 多后端适配层 + 服务层"的三层架构。

概念澄清：CLI、MCP、Skill 到底是什么

在深入对比之前，有必要先澄清三个经常被混用的概念。

CLI（Command Line Interface）

CLI 即命令行接口，是一种通过文本命令与程序交互的方式。在 Agent 工具调用的语境下，CLI 模式指的是：Agent 通过执行 shell 命令（如 mt-tech api "/ddzh/yuding/isvconsume" --developerId "..."）来调用外部工具，工具的输入输出均为文本流（stdin/stdout/stderr）。

CLI 模式的核心特征是：工具本身是一个可执行程序，Agent 通过 bash 等 shell 工具来调用它。Agent 不需要理解工具的内部实现，只需要知道如何拼装命令文本和解析输出文本。

MCP（Model Context Protocol）

MCP 是 Anthropic 于 2024 年底提出的开放协议，旨在为 LLM 应用提供一种标准化的方式来连接外部数据源和工具。MCP 的核心抽象包括：

  • Tools（工具）：LLM 可以调用的函数，每个工具有明确的 JSON Schema 定义输入参数
  • Resources（资源）：LLM 可以读取的数据，如文件、数据库记录等
  • Prompts（提示模板）：可复用的提示词模板

MCP 采用客户端-服务器架构：MCP Client 集成在 Agent 宿主中，负责与 LLM 交互；MCP Server 由工具提供方部署，负责实际执行工具调用。两者通过标准化的 JSON-RPC 协议通信。

Skill

Skill 是一个更高层次的概念，它指的是一份”带使用说明的能力封装”。在本文讨论的语境中，Skill 的形态是：一份带 YAML 头的 Markdown 文档（描述能力、触发条件、使用方法、参数说明、命令模板）+ 一个底层执行工具（可以是 CLI，也可以是 MCP Tool，甚至是 HTTP API）。

Skill 的核心价值在于渐进披露（Progressive Disclosure）：会话开始时只加载 Skill 的名称和简短描述（含触发词），当用户请求命中触发词时，才将完整的使用文档注入 LLM 上下文。这种机制极大地节省了 context 预算。

**关键区分**：CLI 和 MCP 是"执行层"的两种技术方案，而 Skill 是"交互层"的封装模式。Skill 底层既可以挂 CLI，也可以挂 MCP。本文对比的核心是"CLI + Skill"组合 vs "纯 MCP"模式。

真实案例：美团”预约操作”Skill 的 CLI 实践

为了让对比建立在真实工程实践之上，我们以美团 AI Hub 上线的”预约操作”（yuding-operation）Skill 为例。这个 Skill 封装了服务零售业务下的十几个核心接口，包括到店核销、改约、库存同步等，是一个典型的企业级工具接入场景。

Skill 的形态与结构

这个 Skill 的形态极简，由两部分组成：

  1. 一份带 YAML 头的 Markdown 文档（约 49000 字正文），包含：

    • 环境准备说明：检测 mt-tech 是否安装，没有则执行 npm install -g mt-tech
    • 每个接口的参数表（字段名、类型、是否必填、说明）
    • 每个接口的现成调用命令模板
    • 错误码说明和常见问题排查

  2. 一个命令行工具 mt-tech，负责：

    • 请求签名（HMAC-SHA256 等鉴权逻辑）
    • HTTP 请求拼装与发送
    • 响应解析与错误处理
    • 把 JSON 结果输出到 stdout

两种模式的完整交互流程拆解

理解了案例之后，我们来完整拆解两种模式下，Agent 从接收用户请求到返回最终结果的全流程。

CLI 路线：六步交互

以下是美团实际采用的 CLI + Skill 模式的完整交互流程：

  1. 轻量加载：会话开始时，LLM 上下文中只加载该 Skill 的 name + description（含”触发词”），约几十到几百 token。49000 字的正文并不注入。
  2. 触发命中：用户说”帮我核销订单 5008…”，LLM 判断命中触发词，宿主（Agent 框架）把整份 Markdown 正文注入上下文。
  3. 意图理解与参数确认：LLM 阅读文档，判断应该调用 isvconsume 接口，对照参数表发现缺少 orderId，回头向用户确认。
  4. 命令拼装与执行：用户补充参数后，LLM 照模板拼出完整的 mt-tech 命令，在其 bash 工具中执行。
  5. 工具执行：mt-tech 内部完成请求签名、拼装 HTTP、调用美团后端，把 JSON 结果输出到 stdout。LLM 可以在命令中通过管道 | jq '.data' 先过滤结果。
  6. 结果翻译：LLM 读取 stdout 中的（已过滤的）结果，翻译成自然语言回复用户。
**CLI 路线的核心设计哲学**：LLM 只做"理解意图 + 组装命令文本 + 读结果"这一文本层的工作；签名、HTTP、鉴权、重试这些确定性强、最怕编错的逻辑全锁在 CLI 工具里，LLM 碰都不碰。这是一种"信任边界最小化"的设计。

MCP 路线：假设改造

如果把同一个”预约操作”能力改用 MCP 来实现，流程会是这样：

  1. 全量加载：会话一开始，十几个 tool 的 JSON Schema 就全部加载进 LLM 上下文。每个 schema 包含工具名称、描述、参数定义（字段名、类型、是否必填、枚举值等）。
  2. 工具选择：用户说”帮我核销订单 5008…”，LLM 从十几个 tool 中选中 isvconsume，并根据 schema 约束填好 JSON 参数。
  3. 参数校验：如果缺少必填参数（如 orderId），MCP Client 或 LLM 会发现并向用户确认。
  4. 工具调用：MCP Client 向 MCP Server 发起 tool_call 请求，传递 JSON 参数。
  5. 服务端执行：MCP Server 完成签名、HTTP 请求、调用美团后端，获取 JSON 响应。
  6. 全量回灌：MCP Server 把完整的 response payload 返回给 MCP Client，Client 把完整结果全部回灌到 LLM 上下文中。
  7. 结果翻译：LLM 读取完整结果，翻译成自然语言回复用户。

在理解了交互流程之后，我们从七个维度对两种架构进行系统对比。

维度一：说明书位置与加载机制

MCP 将工具的”使用说明书”（即 JSON Schema）内建在协议中。当 MCP Server 启动时，它会向 Client 注册所有可用的 tool 及其 schema，Client 自动将这些 schema 加载到 LLM 的系统提示中。这是一种”协议即文档”的设计——工具的能力描述和参数约束是协议的一部分，不需要额外的文档。

CLI + Skill 模式则将说明书放在外部的 Markdown 文档中。文档不是协议的一部分，而是由宿主（Agent 框架）根据触发词按需注入。这是一种”文档即协议”的设计——工具的使用方法以自然语言文档的形式存在，LLM 通过阅读文档来学习如何使用工具。

深度分析：MCP 的内建 schema 优势在于标准化和自动化——任何支持 MCP 协议的 Client 都能自动发现和使用 Server 提供的工具，无需额外配置。但代价是 schema 必须常驻上下文，因为 LLM 需要随时知道有哪些工具可用、每个工具的参数约束是什么。而 CLI + Skill 的外部文档优势在于灵活性和经济性——文档可以写得非常详细（包含示例、错误码、最佳实践），且只在需要时才注入。但代价是需要宿主框架实现触发词匹配和文档注入逻辑，且不同平台的 Skill 格式可能不统一。

维度二：Context 占用经济学

这是两种架构最核心的差异，也是”CLI 会取代 MCP”这一判断的主要依据。

我们来做一个量化估算。假设一个 MCP Server 提供 15 个 tool，每个 tool 的 schema（含名称、描述、参数定义）平均约 500 token，那么仅 schema 就占用约 7500 token。如果接入 5 个这样的 Server，schema 总量就达到 37500 token。这还不包括每次工具调用后全量回灌的 response payload。

相比之下，CLI + Skill 模式在会话开始时，每个 Skill 只占用 name + description，约 50-100 token。15 个 Skill 总共只占用约 750-1500 token。当用户请求命中某个 Skill 的触发词时，才将该 Skill 的完整文档（可能几千到几万 token）注入上下文。而且注入后，如果后续对话不再需要该 Skill，宿主还可以将其从上下文中移除（或压缩）。

**Context 占用对比（估算）**：接入 15 个工具、5 个服务的场景下，MCP 模式仅 schema 就占用约 37500 token，且每次调用后全量回灌 response；CLI + Skill 模式平时仅占用约 1500 token，命中触发词后才按需注入单个 Skill 的文档。两者相差一个数量级以上。

深度分析：Context 窗口在当前阶段仍是稀缺资源。虽然 GPT-4o、Claude 3.5 等模型已经支持 128K 甚至 200K 的 context 窗口，但：(1) 更长的 context 意味着更高的推理成本和延迟；(2) 模型对长 context 中间部分的信息存在”lost in the middle”现象，召回率下降；(3) 工具调用场景下，context 被 schema 和 response 占用后，留给对话历史和推理的空间就被压缩了。因此，context 经济性不是一个可以忽略的优化点，而是工具调用架构的核心设计约束。

维度五：接入成本与运维负担

对于工具提供方来说，两种模式的接入成本差异显著。

MCP 接入需要：

  • 编写 MCP Server 代码（实现 tool 注册、参数校验、请求处理、响应格式化）
  • 部署和运维一个常驻服务（需要考虑高可用、伸缩、监控、日志）
  • 处理 MCP 协议的版本兼容和安全认证
  • 如果已有 OpenAPI，需要写一层适配层将 REST API 包装成 MCP Tool

CLI + Skill 接入需要：

  • 如果已有 CLI 工具：几乎零成本，只需要写一份 Markdown 文档描述使用方法
  • 如果只有 SDK：将 SDK 包一层 CLI 入口（通常几十行代码），再写文档
  • 如果只有 OpenAPI：用 openapi-generator 等工具自动生成 CLI，再写文档
  • 无需部署常驻服务，CLI 工具在 Agent 本地执行

深度分析：接入成本的不对称性是 CLI 模式的重要优势。对于已经有成熟 OpenAPI 和 SDK 的企业（如美团、阿里、腾讯等），将现有能力包装成 CLI 工具的成本极低，通常只需要几天甚至几小时。而部署一个 MCP Server 则需要投入运维资源，且需要考虑长期的服务稳定性。对于中小团队和个人开发者来说，这种成本差异更为明显——写一个 CLI 工具并发布到 npm/pypi 是轻量级的，而维护一个公网可访问的 MCP Server 则是重量级的。

不过，MCP 的接入成本优势在于标准化和生态。一旦接入 MCP，任何支持 MCP 协议的 Agent 客户端都能自动发现和使用你的工具，无需为每个平台单独适配。而 CLI + Skill 模式目前缺乏统一的 Skill 格式标准，不同 Agent 平台（如豆包、Claude、ChatGPT）的 Skill 格式和加载机制可能不同，工具提供方可能需要为多个平台分别编写 Skill 文档。

维度六：模型亲和性——母语 vs 翻译

这是一个容易被忽视但非常重要的维度。LLM 的本质是文本推理引擎，它在训练过程中接触了海量的文本数据，其中包括大量的 bash 命令、shell 脚本、CLI 工具使用示例。因此，对于当前一代 LLM 来说，bash/CLI 是它的”母语”之一。

当 LLM 需要调用 CLI 工具时，它只需要：(1) 理解用户意图；(2) 对照文档拼装命令文本；(3) 解析 stdout 中的文本结果。整个过程都在文本空间中完成，不需要进行”结构化 ↔ 文本”的转换。

当 LLM 需要调用 MCP Tool 时，它需要：(1) 理解用户意图；(2) 从多个 tool 中选择合适的一个；(3) 根据 JSON Schema 约束构造结构化的参数对象（需要确保字段名正确、类型匹配、必填字段不遗漏）；(4) 解析结构化的 response。这个过程中，LLM 需要在”自然语言意图”和”结构化参数”之间进行转换，相当于做了一次”翻译”。

**模型亲和性的本质**：CLI 是文本接口，与 LLM 的文本推理范式天然对齐；MCP 是结构化接口，需要 LLM 进行"文本→结构化→文本"的转换。虽然当前一代 LLM 已经能够较好地处理结构化调用，但在参数复杂、嵌套层级深、枚举值多的场景下，结构化调用的出错率仍然高于文本命令拼装。

深度分析：模型亲和性的差异会随着模型能力的提升而逐渐缩小。未来的 LLM 可能会在结构化调用方面达到与文本命令相当的准确率。但在当前阶段（2025-2026），bash 命令的准确率仍然有优势，尤其是在需要动态拼装参数、使用变量和循环的复杂场景下。此外，CLI 模式的错误恢复也更友好——如果命令执行失败，LLM 可以直接看到 stderr 中的错误信息，调整命令后重试；而 MCP 调用的错误信息通常被包装在结构化的 error 对象中，LLM 需要解析错误码和错误消息才能理解问题所在。

维度七：确定性与安全边界

这是 MCP 明确占优的维度，也是 CLI 模式不可回避的短板。

MCP 模式下，每个 tool 的输入参数都有明确的 JSON Schema 约束。MCP Client 可以在调用前对参数进行校验，确保字段名、类型、枚举值、必填项都符合约束。这意味着 LLM 不可能”调用一个不存在的工具”，也不可能”传入一个类型错误的参数”。工具的调用面是明确受控的。

此外，MCP Server 运行在独立的进程中（甚至独立的服务器上），与 Agent 宿主隔离。Server 可以实现细粒度的权限控制、审计日志、速率限制等安全机制。MCP 协议本身也支持 OAuth 等标准化认证方式。

CLI 模式下，LLM 拼装的是自由文本的 shell 命令。虽然 Skill 文档中给出了命令模板，但 LLM 完全可能：(1) 拼出模板之外的命令；(2) 传入格式错误的参数；(3) 通过命令注入执行意外操作；(4) 利用 shell 的特性（如 ;、&、|）串联恶意命令。虽然可以通过沙箱、命令白名单、参数校验等机制来缓解，但 CLI 模式的攻击面本质上比 MCP 大。

深度分析：安全边界的差异是 MCP 不可替代的核心理由。在企业级场景中，尤其是涉及支付、用户数据、生产环境操作的场景，安全和确定性是不可妥协的要求。MCP 的 Schema 约束和进程隔离提供了一道坚实的安全防线，而 CLI 模式需要依赖额外的沙箱、白名单、审计机制来弥补，这些机制的实现和维护成本并不低。

不过，CLI 模式的安全风险可以通过工程手段有效缓解。例如：(1) 使用 Docker 等容器沙箱执行 CLI 命令，限制文件系统和网络访问；(2) 实现命令白名单，只允许执行预定义的 CLI 工具和参数模式；(3) 在 CLI 工具内部实现参数校验和权限控制；(4) 对所有命令执行进行审计日志记录。美团等企业在实际生产环境中采用 CLI 模式，说明这些安全缓解措施是有效的。

为什么 CLI 当下在抢 MCP 的地盘：四个驱动力的深度分析

在系统对比之后，我们来深入分析为什么”CLI 会取代 MCP”这一判断会在当下流行。这不是偶然的技术偏好变化，而是四个驱动力同时作用的结果。

驱动力一：Context 成为新的稀缺资源

在 Agent 应用的早期阶段（2023-2024），context 窗口从 4K 扩展到 32K、128K 甚至 200K，业界普遍认为 context 不再是瓶颈。但随着 Agent 工具调用的深入实践，人们发现 context 窗口的扩大并没有解决根本问题：

  • 成本线性增长：LLM 的推理成本与输入 token 数成正比。每次 API 调用都要重新发送完整的 context，schema 常驻意味着每轮对话都要为这些 token 付费。
  • 延迟增加：更长的输入意味着更长的 prefill 时间，用户感知到的响应延迟增加。
  • 注意力稀释：”Lost in the Middle”现象表明，模型对长 context 中间部分的信息召回率显著下降。当 schema 占据了 context 的前几 KB，后续的对话历史和工具结果可能被”忽视”。
  • 多工具膨胀：当 Agent 接入几十个甚至上百个工具时，MCP 的 schema 总量可能达到几十万 token，即使是 200K 窗口也装不下。

在这样的背景下，CLI + Skill 的渐进披露机制天然具有优势。它将 context 占用从”O(工具总数)”降低到”O(当前对话相关工具数)”，这是一个数量级的优化。

驱动力二：模型代码能力的质变

MCP 协议设计的一个核心假设是：LLM 在构造结构化参数时容易出错，需要 JSON Schema 来兜底约束。这个假设在 GPT-3.5 时代是成立的——当时的模型在函数调用时经常出现参数名错误、类型不匹配、嵌套结构混乱等问题。

但从 GPT-4 开始，尤其是 GPT-4o、Claude 3.5 Sonnet、Doubao 1.5 等新一代模型，代码能力发生了质变：

  • bash 命令准确率：当前模型在拼装常见 CLI 命令时的准确率已经超过 95%，即使是包含管道、变量、循环的复杂脚本也能达到较高的正确率。
  • 错误恢复能力：当命令执行失败时，模型能够根据 stderr 中的错误信息自动调整命令并重试，通常 2-3 轮内就能解决问题。
  • 文档理解能力：模型能够快速阅读和理解 Markdown 格式的使用文档，从中提取参数说明和命令模板，并准确应用。

模型代码能力的提升直接稀释了 MCP Schema 兜底的价值。如果 LLM 写 bash 命令已经足够准，那么 Schema 强约束带来的确定性增益就不再明显，而 Schema 常驻带来的 context 成本却实实在在。

**关键趋势**：MCP 的核心价值主张（结构化约束保证确定性）建立在"模型写代码不可靠"的假设上。随着模型代码能力的质变，这个假设正在失效。当兜底的价值被稀释，而兜底的成本（context 占用）依然存在时，架构天平自然向 CLI 模式倾斜。

驱动力三：数据下推的成本优势

第三个驱动力是数据下推（Data Pushdown）带来的成本优势。在 MCP 模式下，每次工具调用的完整 response 都要回灌到 LLM 上下文，这意味着：

  • 每轮对话的输入 token 数随着工具调用次数累积增长
  • 大响应（如列表查询返回几百条记录）会瞬间占用大量 context
  • LLM 需要自己从完整 response 中提取有用信息，增加了推理负担

CLI 模式通过管道过滤实现了数据下推：grep、jq、head、awk 等工具在 shell 层面完成过滤和转换，只有最终结果才进入 LLM 上下文。这不仅节省了 context，还降低了 LLM 的推理负担——它不需要处理原始的大数据集，只需要面对已经清洗和聚合过的结果。

随着 Agent 处理的数据量越来越大（从简单的单条查询到复杂的数据分析、日志处理、批量操作），数据下推的成本优势会越来越明显。这与数据库领域从”全表扫描+应用层过滤”演进到”SQL 下推+数据库层过滤”的历史规律是一致的。

驱动力四：接入成本的不对称性

第四个驱动力是接入成本的不对称。如前文所述，对于已有 OpenAPI 和 SDK 的企业，将能力包装成 CLI 工具的成本远低于部署 MCP Server。这种成本不对称导致了一个正反馈循环：

  1. 工具提供方更愿意提供 CLI 工具（成本低、无需运维）
  2. Agent 平台更愿意支持 CLI + Skill 模式（生态丰富、接入快）
  3. 开发者更熟悉 CLI 工具（学习成本低、调试方便）
  4. 更多 CLI 工具的出现进一步降低了新工具的接入成本（可以复用现有 CLI 框架和模板）

而 MCP 生态的发展则面临”先有鸡还是先有蛋”的问题：没有足够多的 MCP Server，Agent 平台就没有动力深度集成 MCP；没有足够多的 Agent 平台支持 MCP，工具提供方就没有动力部署 MCP Server。虽然 Anthropic 和多家公司在推动 MCP 生态，但 CLI 模式凭借更低的接入成本，在短期内获得了更快的生态增长。

文章的局限性与社区争议

任何技术判断都有其局限性和争议。”CLI 会取代 MCP”这一观点也不例外。我们需要客观地看待其局限性和社区中的反对声音。

争议一：MCP 协议的快速演进——lazyload 与 codemode

“CLI 比 MCP 省 context”这一判断的前提是 MCP 的所有 tool schema 必须常驻上下文。但 MCP 协议本身在快速演进，正在引入解决这个问题的新特性：

  • Lazy Loading（懒加载）：MCP 协议正在讨论和实现 tool schema 的按需加载机制。类似于 CLI + Skill 的渐进披露，MCP Client 可以只加载 tool 的名称和简短描述，当 LLM 选中某个 tool 时，再动态加载该 tool 的完整 schema。这将大幅减少 MCP 模式的 context 占用。
  • Code Mode（代码模式）：MCP 协议的新特性允许 tool 返回可执行的代码片段（如 shell 命令、Python 脚本），由 Agent 宿主在本地执行，而不是将完整结果回灌。这使得 MCP 也能获得 CLI 模式的可组合性和数据下推优势。

如果这些特性成熟并被广泛采用，MCP 在 context 经济性和可组合性上的短板将被大幅弥补。届时，”CLI 比 MCP 省 context”的核心论点将不再成立。

**基准不对等问题**："CLI 会取代 MCP"的论证往往对比的是"先进的 CLI + Skill 实践" vs "经典的 MCP 实现"。如果 MCP 也采用 lazyload、codemode 等新特性，两者的差距会显著缩小。技术对比应该建立在两者都采用最佳实践的基准上。

争议二：0728 新协议带来的变化

2025 年 7 月 28 日，MCP 协议发布了重要更新（社区称为”0728 新协议”），引入了多项增强：

  • 资源模板（Resource Templates）：支持参数化的资源 URI，使得 MCP 可以更灵活地表示动态资源
  • 提示模板（Prompt Templates）：支持可复用的提示词模板，增强了 MCP 的交互能力
  • 进度通知（Progress Notifications）：支持长时间运行的工具调用实时反馈进度
  • 增强的安全模型：改进了认证和授权机制

这些更新表明 MCP 协议正在快速成熟，其能力边界在不断扩展。用早期版本的 MCP 来论证它会被取代，论证基础不够稳固。

争议三：安全边界——CLI 不可回避的短板

如前文所述，CLI 模式在安全边界上存在天然短板。虽然可以通过沙箱、白名单等工程手段缓解，但这些手段的实现和维护成本并不低，且无法完全消除风险。

在企业级生产环境中，尤其是涉及以下场景时，MCP 的安全优势是决定性的：

  • 支付和金融操作：涉及资金流转的操作需要强确定性和审计能力
  • 用户隐私数据：访问和处理用户个人数据需要严格的权限控制
  • 生产环境变更：对生产系统的修改需要可追溯、可回滚
  • 多租户场景：不同租户的数据和操作需要严格隔离

在这些场景下，CLI 模式的灵活性反而成为了风险来源。MCP 的 Schema 约束和进程隔离提供了一道 CLI 模式难以比拟的安全防线。

争议四：非互斥关系——Skill + MCP 的组合可能

社区中一个重要的观点是：CLI 和 MCP 不是互斥的，完全可以组合使用。具体来说：

  • Skill 作为交互层：用 Skill 文档实现渐进披露和触发词匹配，解决 context 经济性问题
  • MCP 作为执行层：Skill 底层挂 MCP Tool，利用 MCP 的标准化、安全边界和认证能力
  • CLI 作为补充：对于已有 CLI 工具的场景，Skill 底层挂 CLI；对于需要强安全的场景，Skill 底层挂 MCP

这种组合模式取两者之长：Skill 层解决了”什么时候加载什么工具”的交互问题，MCP/CLI 层解决了”具体怎么执行”的连接问题。Agent 宿主可以根据场景和工具特性，灵活选择底层执行后端。

事实上，这正是许多 Agent 平台正在演进的方向。豆包的 Skill 体系、Claude 的 Skills、ChatGPT 的 Custom Actions，都在探索”统一交互层 + 多执行后端”的架构。

第一性原理思考：LLM 与工具交互的本质

在对比了具体的技术细节之后，让我们退一步，从第一性原理的角度思考：LLM 与外部工具交互的本质是什么？什么样的架构最符合这个本质？

LLM 是文本推理引擎

大语言模型的本质是一个文本推理引擎。它的输入是文本（token 序列），输出是文本（token 序列），所有的”理解””推理””决策”都发生在文本空间中。模型的训练数据也是文本——书籍、网页、代码、对话等。

这意味着，与 LLM 交互的最自然方式是文本。当工具的输入输出都是文本时，LLM 不需要进行任何格式转换，可以直接在其原生的推理空间中处理。当工具的输入输出是结构化数据（如 JSON 对象）时，LLM 需要在”文本意图”和”结构化参数”之间进行转换，这增加了认知负担和出错概率。

CLI 模式的输入输出都是文本流（命令文本、stdout 文本），与 LLM 的文本推理范式天然对齐。MCP 模式的输入输出是结构化的 JSON 对象，需要 LLM 进行”文本→结构化→文本”的转换。从第一性原理来看，CLI 模式更符合 LLM 的本质。

文本接口 vs 结构化接口的历史轮回

文本接口 vs 结构化接口的争论在技术史上反复出现，每一次都遵循相似的规律：

时代 结构化方案 文本/轻量方案
1990s-2000s CORBA / DCOM / SOAP（XML Schema、强类型、标准化协议栈） REST（JSON、HTTP 原生、灵活路由）
2000s-2010s SOAP Web Services（WSDL、UDDI、WS-* 协议族） RESTful API（OpenAPI/Swagger、JSON、HTTP 动词）
2010s-2020s gRPC（Protobuf、强类型、HTTP/2、代码生成） GraphQL（灵活查询、文本查询语言）/ tRPC（类型推断）
2020s-现在 MCP（JSON Schema、标准化协议、Client-Server） CLI + Skill（文本命令、Markdown 文档、渐进披露）

历史规律很清晰：

  1. 结构化方案先出现，在技术早期提供了标准化和强类型的保障
  2. 文本/轻量方案后出现，凭借更低的接入成本和更好的灵活性赢得主流市场
  3. 结构化方案没有死，在对性能、安全、确定性要求高的场景（企业内部、金融、电信）中持续存在
  4. 最终是分层共存：主流场景用轻量方案，关键场景用结构化方案，两者通过适配层互通

SOAP vs REST 的结局是：REST 成为了互联网 API 的事实标准，但 SOAP 在银行、电信、企业内部集成中仍有大量应用；gRPC 在微服务内部通信中占优，但对外 API 仍以 REST/GraphQL 为主。

按照这个规律，MCP vs CLI 的结局很可能也是：CLI + Skill 成为 Agent 工具调用的主流方案，MCP 在需要强安全和标准化的企业级场景中持续存在，两者通过适配层互通。

**历史类比的启示**：技术史上从来没有"谁彻底取代谁"，只有"主战场迁移"。REST 没有"杀死"SOAP，只是把主战场从企业内部搬到了互联网开放 API。同样，CLI 不会"杀死"MCP，只是把 Agent 工具调用的主战场从"标准化连接"搬到了"经济高效的交互"。理解这一点，就不会陷入非此即彼的站队思维。

未来收敛：三层架构模型

基于以上分析，我认为 Agent 工具调用架构最终会收敛到三层模型。这不是 CLI 取代 MCP，也不是 MCP 吃掉 CLI，而是两者在不同层级上各司其职。

第一层：Skill 交互层

交互层负责”什么时候用什么工具、怎么向 LLM 展示工具”。核心组件包括：

  • Skill 文档：一份带 YAML 头的 Markdown，包含名称、描述、触发词、使用方法、参数说明、命令模板、示例等
  • 渐进披露机制：会话开始时只加载 name + description，命中触发词后才注入完整正文，对话结束后可移除或压缩
  • 上下文管理：负责 Skill 文档的注入、移除、压缩，以及工具调用结果的过滤和回灌策略

交互层是与 LLM 直接对接的层面，它的核心目标是在最少的 context 消耗下，让 LLM 能够正确地选择和使用工具。交互层不关心底层工具是 CLI 还是 MCP，它只关心”如何向 LLM 描述工具能力”和”何时注入/移除工具描述”。

第二层：多后端适配层

适配层负责”具体怎么执行工具调用”。它是一个插件化的架构，支持多种执行后端：

  • CLI 适配器：通过 bash 执行命令行工具，支持管道过滤和变量替换。适用于已有 CLI 工具的场景，以及需要高可组合性的场景。
  • MCP 适配器：通过 MCP 协议调用 MCP Server 上的 tool，支持 schema 校验和标准化认证。适用于需要强安全和标准化的场景，以及第三方 SaaS 提供了 MCP Server 的场景。
  • HTTP 适配器：直接调用 REST API。适用于简单的 API 调用场景，无需额外的 CLI 或 MCP Server。
  • SDK 适配器：直接调用本地函数或 SDK。适用于需要高性能和低延迟的场景，以及工具逻辑本身就在 Agent 进程内的场景。

适配层的核心目标是为不同特性的工具提供最合适的执行方式，同时对上层交互层屏蔽底层差异。Skill 文档中可以指定使用哪个适配器，或者由宿主根据工具特性自动选择。

第三层：服务层

服务层是实际的业务逻辑和数据来源，包括：

  • 企业内部服务：如美团的预约操作 API、阿里的电商 API、腾讯的社交 API 等。这些服务通常已有成熟的 OpenAPI 和 SDK。
  • 第三方 SaaS：如 Slack、Notion、GitHub、Salesforce 等。这些服务可能提供 MCP Server、CLI 工具或 REST API。
  • 本地工具：如文件系统操作、Shell 脚本、数据库查询、本地计算等。这些工具通常以 CLI 或 SDK 的形式存在。
  • AI 服务：如搜索引擎、代码解释器、图像生成、语音识别等。这些服务通常以 API 的形式提供。

服务层的核心目标是提供实际的业务能力，它不关心上层用什么协议和架构来调用。

三层架构的优势

三层架构的核心优势在于关注点分离：

  • 交互层专注于 LLM 体验：context 经济性、触发准确性、使用便捷性
  • 适配层专注于执行效率：根据工具特性选择最合适的执行方式，平衡灵活性和安全性
  • 服务层专注于业务能力：提供稳定、可靠、高性能的服务

这种架构使得各层可以独立演进：交互层可以优化渐进披露算法，适配层可以增加新的执行后端，服务层可以扩展业务能力，三者互不干扰。同时，它也避免了”非此即彼”的站队——CLI 和 MCP 都可以作为适配层的一种后端，根据场景灵活选择。

选型决策框架

理论分析之后，我们来给出可操作的选型决策框架。当你需要为 Agent 接入一个新工具时，可以按照以下框架来决策。

什么时候选 CLI + Skill

满足以下条件中的多数时，CLI + Skill 是更优选择：

  • 已有 CLI 工具或 SDK：工具提供方已经有成熟的命令行工具或 SDK，包一层 Skill 文档的成本极低
  • Context 敏感：Agent 需要接入大量工具（几十个以上），context 预算紧张
  • 需要高可组合性：工具调用经常需要多步组合、管道过滤、循环批量操作
  • 数据量大：API 返回的数据量较大，需要在 shell 层面先过滤再回灌
  • 快速迭代：工具能力变化频繁，需要快速更新使用文档而无需重新部署服务
  • 内部工具：工具在企业内部或可信环境中使用，安全风险可控
  • 开发者友好：目标用户是开发者，熟悉命令行操作，需要灵活的调试能力

什么时候选 MCP

满足以下条件中的多数时，MCP 是更优选择：

  • 强安全要求：工具涉及支付、用户隐私、生产环境变更等敏感操作，需要 Schema 强约束和进程隔离
  • 第三方 SaaS 接入：需要接入多个第三方服务，希望通过标准化协议统一接入，避免为每个平台单独适配
  • 多平台分发：工具需要被多种 Agent 客户端（Claude、ChatGPT、豆包等）使用，MCP 的标准化可以降低跨平台适配成本
  • 统一认证授权：需要 OAuth 等标准化认证机制，以及细粒度的权限控制
  • 审计合规：需要统一的调用审计日志，满足合规要求
  • 工具数量少：Agent 只接入少量工具（十个以下），context 占用不是瓶颈
  • 零容错场景：参数错误会导致严重后果，需要 Schema 校验来兜底

什么时候混合使用

在大多数实际场景中，混合使用是最佳策略：

  • 内部工具用 CLI，外部 SaaS 用 MCP：内部已有 CLI 工具的场景走 CLI，第三方 SaaS 提供了 MCP Server 的走 MCP
  • 查询类操作用 CLI，变更类操作用 MCP：查询、搜索、分析等只读操作可以用 CLI（灵活、可组合），创建、修改、删除等写操作用 MCP（安全、可控）
  • 高频工具用 CLI，低频工具用 MCP：高频使用的工具用 CLI 节省 context，低频使用的工具用 MCP 享受标准化
  • Skill 层统一，底层灵活选择：所有工具都用 Skill 文档做交互层，底层根据工具特性挂 CLI 或 MCP

决策检查清单

在做最终决策前，对照以下清单逐项检查：

  1. 工具特性：这个工具有没有现成的 CLI？有没有 MCP Server？只有 REST API？
  2. 安全等级：这个工具的操作是否涉及资金、隐私、生产变更？出错的后果有多严重？
  3. 使用频率：这个工具在 Agent 对话中会被高频调用还是低频调用？
  4. 数据规模：这个工具的返回数据量有多大？是否需要过滤和聚合？
  5. 组合需求：这个工具是否经常需要与其他工具组合使用？是否需要批量操作？
  6. 工具总数：Agent 总共会接入多少个工具？context 预算是否紧张？
  7. 分发范围：这个工具需要被多少种 Agent 客户端使用？是否需要跨平台标准化？
  8. 运维能力：团队是否有能力部署和运维一个常驻 MCP Server？
  9. 迭代速度：工具的能力和接口是否频繁变化？需要多快的更新速度？
  10. 用户画像：最终用户是开发者还是普通用户？是否需要命令行级别的灵活性？

实践建议与最佳实践

最后，给出一些在实际工程中可以直接应用的最佳实践。

CLI + Skill 最佳实践

  1. Skill 文档结构标准化：统一使用 YAML 头 + Markdown 正文的格式，YAML 头包含 name、description、triggers（触发词）、version、author 等元数据；正文包含环境准备、接口列表、参数表、命令模板、示例、错误码、常见问题等章节。
  2. 触发词设计要精准：触发词应该是用户自然会说的短语，且具有足够的区分度。避免使用过于宽泛的词（如”查询””处理”），以免误触发。可以设计多个触发词覆盖不同的用户表达习惯。
  3. 命令模板要可直接复制：Skill 文档中的命令模板应该包含完整的参数和示例值，LLM 可以直接复制后修改参数。避免使用过于抽象的占位符，尽量给出真实的示例值。
  4. 结果过滤要前置：在命令模板中默认包含管道过滤（如 | jq '.data'），确保只有有用的结果进入 stdout。对于列表查询，默认加上 head -N 限制返回条数。
  5. 安全沙箱不可省：即使是内部工具，CLI 命令也应该在沙箱中执行。使用 Docker 容器限制文件系统和网络访问，实现命令白名单，对所有执行进行审计日志。
  6. 错误信息要友好：CLI 工具的 stderr 应该输出清晰、可理解的错误信息，包含错误码、错误原因和修复建议。LLM 可以根据错误信息自动调整命令并重试。

MCP 最佳实践

  1. Schema 设计要精简：每个 tool 的 schema 只包含必要的参数，避免冗余字段。参数描述要清晰准确，使用枚举值限制输入范围。对于复杂的嵌套参数，考虑拆分为多个 tool。
  2. Tool 粒度要适中：避免设计过于原子化的 tool（需要多次调用才能完成一个完整操作），也避免设计过于庞大的 tool（一个 tool 做太多事情，参数复杂）。每个 tool 应该对应一个完整的、有意义的业务操作。
  3. 响应数据要克制：tool 的 response 只返回 LLM 需要的字段，避免返回完整的数据库记录。对于列表查询，支持分页和字段选择参数，让 LLM 可以控制返回数据量。
  4. 安全认证要标准化：使用 OAuth 2.0 等标准化认证协议，实现细粒度的权限控制。对每个 tool 定义所需的权限 scope，MCP Client 在调用前检查权限。
  5. 错误处理要规范：使用标准化的错误码和错误消息，包含可重试标识和修复建议。对于长时间运行的操作，使用进度通知机制实时反馈状态。
  6. 考虑 lazyload 兼容：在设计 MCP Server 时，考虑未来 lazyload 特性的兼容。将 tool 按功能分组，支持按组加载 schema，减少常驻 context。

混合架构最佳实践

  1. 统一 Skill 交互层：无论底层是 CLI 还是 MCP，都用统一的 Skill 文档格式做交互层。Skill 文档中指定底层执行后端（CLI/MCP/HTTP），宿主根据指定选择适配器。
  2. 适配器插件化：将 CLI 适配器、MCP 适配器、HTTP 适配器设计为插件化架构，支持动态加载和扩展。新的执行后端可以通过插件形式加入，无需修改核心框架。
  3. 上下文统一管理：由交互层统一管理所有工具的上下文注入和移除，不管底层是什么后端。实现基于 LRU 或相关性的上下文淘汰策略，确保 context 预算不被耗尽。
  4. 安全策略分层：在交互层实现统一的安全策略（如敏感操作确认、调用频率限制），在适配层实现后端特定的安全机制（如 CLI 沙箱、MCP Schema 校验）。两层安全机制叠加，提供纵深防御。
  5. 可观测性统一：实现统一的调用日志、指标采集和链路追踪，不管底层是什么后端。可以清晰地看到每个工具调用的耗时、成功率、context 消耗等指标，用于优化和排障。

结论：不是取代，是主战场迁移

经过以上深度分析，我们可以得出以下结论：

**第一，”CLI 会取代 MCP”是一个过度简化的判断。**CLI + Skill 模式在 context 经济性、可组合性、接入成本和模型亲和性上确实具有显著优势，这些优势在当前阶段（模型代码能力质变、context 仍是稀缺资源）尤为突出。但 MCP 在标准化、安全边界和认证授权上的优势是 CLI 模式难以替代的，尤其是在企业级和高安全场景中。

**第二，更准确的判断是”主战场迁移”。**CLI 正在抢走 Agent 工具调用的”交互层”主战场——因为省 context、强组合、复用生态、模型够可靠这四点在此刻同时成立。但在”连接层”，MCP 的标准化、认证与安全边界短期内 CLI 替代不了。这与历史上 SOAP vs REST、CORBA vs REST 的演进规律一致：轻量方案赢得主流，结构化方案守住关键场景，最终分层共存。

**第三，未来的收敛形态是三层架构。**Skill 交互层负责渐进披露和上下文管理，多后端适配层支持 CLI/MCP/HTTP/SDK 等多种执行方式，服务层提供实际业务能力。这种架构取两者之长，避免了非此即彼的站队。CLI 和 MCP 都可以作为适配层的一种后端，根据工具特性和场景灵活选择。

**第四，对于实践者来说，关键不是选边，而是理解各自的适用场景。**内部工具、查询操作、高频调用、大数据量的场景倾向 CLI；第三方 SaaS、变更操作、低频调用、高安全的场景倾向 MCP。大多数实际场景下，混合使用是最佳策略。用统一的 Skill 交互层封装，底层根据需要挂 CLI 或 MCP，这是面向未来的架构选择。

**最终一句话**：把"取代"理解成"主战场迁移"，把"选边"理解成"分层选型"，把"对立"理解成"互补共存"——这才是看待 CLI vs MCP 之争的正确姿势。最终赢的不是某一个协议，而是把 context 经济性、安全性和灵活性都刻进设计 DNA 的那一方。

关于本文：本文基于美团开放平台”预约操作”Skill 的真实实践，结合 MCP 协议的最新演进和社区讨论，从第一性原理和历史类比的角度进行深度分析。文中观点仅代表技术分析视角，不构成任何产品或技术选型的最终建议。实际选型应结合具体业务场景、团队能力和安全要求综合判断。

这里限定的表达式求值问题是：用户输入一个包含“+”、“-”、“_”、“/”、正整数和圆括号的合法数学表达式，计算该表达式的运算结果。在程序语言中，运算符位于两个操作数中间的表达式称为中缀表达式。例如： 1+2_3
就是一个中缀表达式，中缀表达式是最常用的一种表达式方式。对中缀表达式的运算一般遵循“先乘除，后加减，从左到右计算，先括号内，后括号外”的规则。因此，中缀表达式不仅要依赖运算符优先级，而且还要处理括号。
表达式有前缀、中缀和后缀表示法。
OP + S1 + S2 为前缀表示法
S1 + OP + S2 为中缀表示法
S1 + S2 + OP 为后缀表示法
经过分析，表达式的三种表示法有以下特点：:操作数之间的相对次序不变；运算符的相对次序不同；若中缀式丢失括号信息，则运算的次序不确定；后缀和前缀表达式中已考虑了运算符的优先级，没有括号，只有操作数和运算符。
所以，算术表达式求值过程是： STEP 1：先将算术表达式转换成后缀（前缀）表达式。 STEP 2：然后对该后缀（前缀）表达式求值。
层次一：中缀式—》后缀式—》求值。
层次二：中缀式—》前缀式—》求值

FROM departments d，employees e
WHERE e.’department_id’=d.’department_id’
GROUP BY department_name
HAVING COUNT()>3;
ORDER BY COUNT(*) DESC;

SELECT department_name,COUNT’‘ 员工个数
FROM employees e
INNER JOIN departments d
ON e.’department_id’=d.’department_id’
GROUP BY department_name
HAVING COUNT()>3;
ORDER BY COUNT(*) DESC;
